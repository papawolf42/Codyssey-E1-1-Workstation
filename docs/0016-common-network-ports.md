# 자주 사용하는 네트워크 포트 번호 정리

> 웹, 원격 접속, DNS, 이메일, 파일 전송, 데이터베이스에서 자주 접하는 기본 포트 치트시트

## 1. 포트란?

IP 주소가 네트워크에서 **컴퓨터를 찾는 주소**라면, 포트 번호는 그 컴퓨터 안에서 **어떤 서비스와 통신할지 구분하는 번호**다.

```text
IP 주소                    포트
어느 컴퓨터인가?           그 컴퓨터의 어느 서비스인가?

192.168.0.10:80
└─────┬─────┘ └┬┘
      IP       port
```

아파트에 비유하면:

```text
IP 주소 = 아파트 건물 주소
포트 번호 = 건물 안의 호수
프로토콜 = 대화하고 데이터를 주고받는 규칙
```

하나의 IP 주소에서도 포트가 다르면 서로 다른 서비스를 운영할 수 있다.

```text
example.com:22   → SSH 원격 접속
example.com:80   → HTTP 웹 서버
example.com:443  → HTTPS 웹 서버
```

---

## 2. “미리 정해진 포트”의 정확한 의미

HTTP는 80, HTTPS는 443처럼 서비스별로 널리 사용하는 **기본 포트**가 등록되어 있다. IANA가 서비스 이름과 전송 프로토콜별 포트 번호 등록부를 관리한다.

그러나 포트가 기술적으로 완전히 고정된 것은 아니다.

- HTTP 서버를 8080번에서 실행할 수 있다.
- SSH 서버를 2222번에서 실행할 수 있다.
- 클라이언트가 기본값이 아닌 포트를 사용하려면 포트 번호를 명시해야 한다.
- 포트를 변경해도 프로토콜 자체가 다른 프로토콜로 변하지 않는다.
- 포트 번호만 보고 실제 서비스나 보안 여부를 100% 확정할 수는 없다.

예:

```text
http://example.com
→ HTTP 기본 포트 80이 생략됨

http://example.com:8080
→ HTTP를 8080번 포트로 사용

https://example.com
→ HTTPS 기본 포트 443이 생략됨
```

핵심 답안:

> 포트 번호는 특정 프로토콜을 강제로 결정하는 값이 아니라, 서비스 식별을 위해 등록되고 관례적으로 사용하는 기본 번호다. 서버 설정에 따라 다른 포트를 사용할 수 있다.

## 3. 포트 번호 범위

포트 번호는 16비트 값으로 `0`부터 `65535`까지 존재한다.

| 범위 | 이름 | 주요 용도 |
|---:|---|---|
| `0–1023` | System Ports, Well-Known Ports | HTTP, HTTPS, SSH, DNS 같은 핵심 서비스 |
| `1024–49151` | User Ports, Registered Ports | 애플리케이션·제품별 등록 서비스 |
| `49152–65535` | Dynamic/Private Ports | 클라이언트 임시 포트와 사설 용도 |

### 서버 포트와 클라이언트 임시 포트

브라우저가 HTTPS 서버에 접속하는 예:

```text
클라이언트                      서버
192.168.0.20:53124  ─────▶  203.0.113.10:443
              └┬──┘                    └┬┘
          임시 출발 포트          HTTPS 서비스 포트
```

서버는 보통 알려진 포트에서 기다리고, 클라이언트 운영체제는 통신을 구분하기 위한 임시 출발 포트를 자동으로 선택한다.

## 4. TCP와 UDP

포트 번호는 TCP와 UDP에 각각 존재한다. 따라서 `53/TCP`와 `53/UDP`는 번호는 같지만 서로 다른 전송 프로토콜의 포트다.

| TCP | UDP |
|---|---|
| 연결 지향 | 비연결형 |
| 전달·순서·재전송 처리 | 전달 보장보다 단순성과 속도에 중점 |
| 웹, SSH, 이메일 등에 널리 사용 | DNS 질의, DHCP, NTP 등에 널리 사용 |

주의:

- “TCP는 무조건 느리고 UDP는 무조건 빠르다”로만 이해하면 안 된다.
- 애플리케이션 프로토콜의 설계와 네트워크 상황도 성능에 영향을 준다.
- HTTP/3은 QUIC 위에서 동작하며 QUIC은 UDP를 사용한다.

## 5. 시험 필수 포트

| 포트 | 전송 | 서비스·프로토콜 | 용도 |
|---:|---|---|---|
| `20` | TCP | FTP data | 전통적인 FTP 능동 모드 데이터 전송 |
| `21` | TCP | FTP control | FTP 명령·제어 연결 |
| `22` | TCP | SSH | 암호화된 원격 셸·SFTP·SCP |
| `23` | TCP | Telnet | 암호화되지 않은 원격 터미널 |
| `25` | TCP | SMTP | 메일 서버 간 이메일 전송 |
| `53` | UDP/TCP | DNS | 도메인 이름과 IP 주소 변환 |
| `67` | UDP | DHCP server | DHCP 서버 |
| `68` | UDP | DHCP client | DHCP 클라이언트 |
| `80` | TCP | HTTP | 암호화되지 않은 웹 통신 |
| `110` | TCP | POP3 | 메일 수신·다운로드 |
| `123` | UDP | NTP | 네트워크 시간 동기화 |
| `143` | TCP | IMAP | 서버에 메일을 두고 동기화 |
| `443` | TCP/UDP | HTTPS | TLS로 보호되는 HTTP, UDP는 HTTP/3 계열에서 사용 |
| `445` | TCP | SMB | Windows 파일·프린터 공유 |
| `587` | TCP | Message Submission | 이메일 클라이언트의 메일 제출 |
| `993` | TCP | IMAPS | TLS로 보호되는 IMAP |
| `995` | TCP | POP3S | TLS로 보호되는 POP3 |

시험 직전 암기:

```text

22    SSH
23    Telnet
25    SMTP
53    DNS
67/68 DHCP
80    HTTP
110   POP3
123   NTP
143   IMAP
443   HTTPS
445   SMB
587   메일 제출
993   IMAPS
995   POP3S
```

## 6. 웹 관련 포트

| 포트 | 전송 | 이름 | 설명 |
|---:|---|---|---|
| `80` | TCP | HTTP | 일반적인 HTTP 기본 포트 |
| `443` | TCP | HTTPS | TLS를 사용하는 HTTP 기본 포트 |
| `443` | UDP | HTTPS/QUIC 계열 | HTTP/3에서 일반적으로 사용 |
| `8080` | TCP | HTTP alternate | 개발 서버·프록시에서 자주 사용하는 대체 HTTP 포트 |
| `8443` | TCP | HTTPS alternate 관례 | 개발·관리 서비스의 대체 HTTPS 포트로 자주 사용 |

### URL에서 기본 포트 생략

```text
http://example.com
= http://example.com:80

https://example.com
= https://example.com:443
```

### 8080은 왜 자주 사용하는가?

80번과 비슷해 기억하기 쉽고, 개발용 웹 서버나 프록시의 대체 포트로 널리 사용된다. 또한 일부 운영체제에서는 낮은 포트에 바인딩할 때 더 높은 권한이 필요할 수 있어 일반 사용자 개발 환경에서 8080 같은 높은 포트를 사용하기도 한다.

하지만 `8080`이 항상 HTTP라는 뜻은 아니다. 실제 서비스는 서버 설정으로 결정된다.

## 7. HTTPS란?

HTTPS는 **Hypertext Transfer Protocol Secure**의 약어다.

쉽게 말하면:

```text
HTTPS = HTTP + TLS 보안 통신
```

HTTP가 웹 브라우저와 서버 사이에서 요청과 응답을 주고받는 규칙이라면, HTTPS는 그 HTTP 통신을 TLS로 보호한다.

```text
HTTP
브라우저 ───── 평문 HTTP 통신 ─────▶ 서버

HTTPS
브라우저 ───── TLS로 보호된 HTTP 통신 ─────▶ 서버
```

HTTPS의 기본 포트는 `443`이다.

```text
http://example.com   → 기본 TCP 포트 80
https://example.com  → 기본 TCP 포트 443
```

### HTTPS가 제공하는 세 가지 핵심

| 보호 기능 | 의미 |
|---|---|
| 기밀성 | 통신 내용을 암호화하여 중간에서 쉽게 읽지 못하게 함 |
| 무결성 | 전송 중 데이터가 몰래 변경되었는지 확인 |
| 인증 | 인증서를 통해 접속한 서버의 신원을 검증 |

시험 답안:

> HTTPS는 HTTP 통신을 TLS로 보호하는 방식이다. 일반적으로 443번 포트를 사용하며, 암호화를 통한 기밀성, 데이터 변경 탐지를 위한 무결성, 인증서를 이용한 서버 인증을 제공한다.

### TLS란?

TLS는 **Transport Layer Security**의 약어다.

TLS는 브라우저와 서버 사이에 보안 통신 채널을 만든다. 현대 HTTPS에서 사용하는 보안 프로토콜이며, 과거의 SSL을 계승한다.

```text
SSL = Secure Sockets Layer
TLS = Transport Layer Security
```

일상적으로 “SSL 인증서”라고 부르는 경우가 많지만, 현대 웹 통신에서는 실제로 TLS가 사용된다.

### 인증서란?

HTTPS 서버는 브라우저에 디지털 인증서를 제시한다. 인증서에는 일반적으로 다음과 같은 정보가 포함된다.

- 인증서가 적용되는 도메인
- 서버의 공개키와 관련 정보
- 인증서를 발급한 인증 기관
- 인증서 유효 기간
- 인증 기관의 디지털 서명

브라우저는 다음을 확인한다.

1. 접속한 도메인과 인증서의 도메인이 일치하는가?
2. 인증서의 유효 기간이 지나지 않았는가?
3. 신뢰할 수 있는 인증 기관으로 이어지는가?
4. 인증서의 서명이 유효한가?
5. 인증서가 통신에 사용하기에 적절한가?

### 인증 기관이란?

CA는 **Certificate Authority**, 즉 인증 기관이다.

```text
사용자 브라우저
      │
      │ 신뢰할 수 있는 CA 목록 보유
      ▼
인증 기관(CA)
      │
      │ 서버 인증서 서명
      ▼
example.com 인증서
```

브라우저는 운영체제나 브라우저가 신뢰하는 CA를 기준으로 서버 인증서의 신뢰 경로를 검사한다.

### HTTPS 접속 과정

아래는 이해를 위한 단순화된 흐름이다.

```text
1. 브라우저가 example.com의 IP 주소를 DNS로 확인
2. 서버의 443번 포트에 연결
3. 브라우저와 서버가 TLS 버전·암호 방식 등을 협상
4. 서버가 인증서를 제시
5. 브라우저가 도메인·유효 기간·서명·신뢰 경로 확인
6. 양쪽이 통신에 사용할 세션 키를 안전하게 합의
7. 이후 HTTP 요청과 응답을 암호화하여 전송
```

이를 흔히 **TLS handshake**, 즉 TLS 핸드셰이크라고 부른다.

```text
브라우저                           서버
   │──── 지원 가능한 TLS 정보 ────▶│
   │◀──── 서버 선택·인증서 ────────│
   │──── 인증서 확인·키 합의 ─────▶│
   │                               │
   │◀══ 암호화된 HTTPS 통신 ══════▶│
```

### 공개키와 세션 키를 모두 사용하는 이유

HTTPS는 개념적으로 서로 다른 암호 기술의 장점을 함께 사용한다.

- 공개키 기반 기술: 서버 인증과 안전한 키 합의
- 대칭키 기반 기술: 실제 대량 데이터의 빠른 암호화

핸드셰이크를 통해 통신용 키를 합의한 뒤, 실제 HTTP 데이터는 효율적인 대칭키 암호 방식으로 보호한다.

### HTTP와 HTTPS 비교

| HTTP | HTTPS |
|---|---|
| Hypertext Transfer Protocol | Hypertext Transfer Protocol Secure |
| 기본 포트 80 | 기본 포트 443 |
| 자체적으로 전송 내용을 암호화하지 않음 | TLS로 통신 보호 |
| 중간자가 내용을 읽거나 바꿀 위험 | 도청·변조·위조 방어를 제공 |
| `http://` | `https://` |

중요:

> HTTPS는 HTTP의 내용을 보호하는 것이지, HTTP와 완전히 무관한 별도 웹 문서 형식이 아니다.

### HTTPS가 보호하는 것

HTTPS가 정상적으로 구성되면 네트워크 중간자는 다음 정보를 쉽게 읽거나 변경할 수 없다.

- URL의 경로와 쿼리
- HTTP 헤더
- 쿠키
- 로그인 요청 내용
- 전송되는 웹 페이지와 API 데이터

다만 통신에 필요한 일부 메타데이터는 환경과 프로토콜에 따라 관찰될 수 있다.

- 접속 상대의 IP 주소
- 트래픽의 시간과 크기
- 일부 환경에서의 도메인 관련 정보

HTTPS가 모든 네트워크 흔적을 숨겨 주는 것은 아니다.

### 자물쇠 표시가 의미하는 것

브라우저의 HTTPS 표시가 의미하는 핵심:

> 현재 브라우저와 인증서에 표시된 도메인 사이의 통신이 TLS로 보호되고 있다.

하지만 다음까지 보장하지는 않는다.

- 사이트 운영자가 선량하다는 것
- 판매 상품이나 정보가 진짜라는 것
- 악성 코드가 절대 없다는 것
- 사용자가 입력한 정보가 서버 내부에서 안전하게 보관된다는 것
- 피싱 사이트가 아니라는 것

공격자도 자신이 소유한 피싱 도메인에 정상 HTTPS 인증서를 발급받을 수 있다. 따라서 HTTPS 표시뿐 아니라 **정확한 도메인 이름**도 확인해야 한다.

### 인증서 오류가 발생하는 이유

대표적인 원인:

| 오류 원인 | 설명 |
|---|---|
| 도메인 불일치 | 접속 주소와 인증서 대상 도메인이 다름 |
| 유효 기간 만료 | 인증서 사용 기간이 끝남 |
| 신뢰할 수 없는 CA | 브라우저가 발급자를 신뢰하지 않음 |
| 자체 서명 인증서 | 공인 CA가 아닌 서버 자신이 서명 |
| 중간 인증서 누락 | 서버의 인증서 체인이 완전하지 않음 |
| 잘못된 시스템 시간 | 인증서 유효 기간 판단이 어긋남 |

인증서 경고를 무조건 무시하고 접속하면 중간자 공격이나 잘못된 서버에 연결될 위험이 있다.

### localhost 개발 환경의 HTTPS

현재 과제에서는 다음처럼 HTTP를 사용한다.

```text
http://localhost:8080
```

개발 환경에서 HTTPS를 사용하려면 추가로 인증서와 TLS를 처리할 서버 설정이 필요하다.

```text
https://localhost:8443
```

자체 서명 인증서를 사용하면 암호화 자체는 가능하지만, 브라우저가 해당 인증서를 기본적으로 신뢰하지 않아 경고를 표시할 수 있다. 로컬 개발에서는 개발용 CA나 프록시 도구를 사용하기도 한다.

### Docker에서 HTTPS를 구성하는 개념

일반적인 구조 중 하나:

```text
사용자
  │
  │ HTTPS :443
  ▼
Nginx 또는 리버스 프록시
  │ TLS 인증서 처리
  │
  │ 내부 HTTP
  ▼
애플리케이션 컨테이너 :3000
```

리버스 프록시가 외부 HTTPS 연결과 인증서를 처리하고, 내부 네트워크의 애플리케이션에 요청을 전달할 수 있다. 이를 **TLS termination**이라고 부른다.

Docker 포트 예:

```bash
docker run -d \
  -p 443:443 \
  secure-nginx-image
```

단, `-p 443:443`만 지정한다고 HTTPS가 자동으로 생기는 것은 아니다. 컨테이너 안의 서버가 인증서와 개인키를 사용해 TLS 통신을 처리하도록 별도로 설정되어 있어야 한다.

### HTTPS와 포트에 관한 함정

1. 443번 포트를 사용한다고 무조건 HTTPS는 아니다.
2. HTTPS는 443번 이외의 포트에서도 실행할 수 있다.
3. `EXPOSE 443`만으로 TLS 설정이나 인증서가 만들어지지 않는다.
4. `-p 443:443`은 포트만 연결하며 암호화 기능을 추가하지 않는다.
5. 인증서의 공개키는 공개되어도 되지만 개인키는 절대 노출하면 안 된다.

예:

```text
https://example.com:8443
```

HTTPS를 8443번 포트에서 사용하는 URL이다. 기본 포트 443이 아니므로 URL에 포트를 직접 적는다.

### HTTPS 한 줄 암기

> HTTPS는 HTTP를 TLS로 보호하여 서버 인증, 통신 암호화, 데이터 무결성을 제공하며 기본 포트는 443이다.

## 8. 현재 Docker 과제의 포트

Dockerfile:

```dockerfile
FROM nginx:alpine

COPY site/index.html /usr/share/nginx/html/index.html

EXPOSE 80
```

실행:

```bash
docker run -d \
  --name first-nginx-container \
  -p 8080:80 \
  first-built-image
```

해석:

```text
브라우저 또는 curl
http://localhost:8080
          │
          │ Docker 포트 매핑
          ▼
컨테이너의 80번 포트
Nginx HTTP 서버
```

```text
-p 8080:80
   └┬──┘ └┬┘
   host  container
```

- 호스트에서는 `8080`으로 접속한다.
- 컨테이너의 Nginx는 기본 HTTP 포트인 `80`에서 대기한다.
- Docker가 호스트 8080번 요청을 컨테이너 80번으로 전달한다.

### `EXPOSE 80`과 `-p 8080:80`

| `EXPOSE 80` | `-p 8080:80` |
|---|---|
| 이미지가 80번 포트를 사용할 예정이라고 문서화 | 실제 호스트·컨테이너 포트 연결 생성 |
| Dockerfile에 작성 | `docker run` 실행 시 지정 |
| 이것만으로 호스트 접속 불가 | 호스트의 8080으로 접속 가능 |

## 9. 원격 접속 포트

| 포트 | 전송 | 프로토콜 | 특징 |
|---:|---|---|---|
| `22` | TCP | SSH | 암호화된 원격 접속 |
| `23` | TCP | Telnet | 평문 기반 원격 접속 |
| `3389` | TCP/UDP | RDP | Windows 원격 데스크톱 |

### SSH와 Telnet 비교

| SSH | Telnet |
|---|---|
| 기본 포트 22 | 기본 포트 23 |
| 통신 암호화 | 기본적으로 평문 |
| 현대 원격 관리에 사용 | 보안상 일반 인터넷 환경에서 권장되지 않음 |

```bash
ssh user@example.com
```

기본적으로 22번 포트를 사용한다.

다른 포트를 사용하는 SSH 서버:

```bash
ssh -p 2222 user@example.com
```

여기서 `-p 2222`는 SSH가 22번 대신 2222번 포트로 접속하게 한다.

## 10. DNS와 네트워크 설정 포트

| 포트 | 전송 | 프로토콜 | 역할 |
|---:|---|---|---|
| `53` | UDP/TCP | DNS | 이름 조회와 DNS 데이터 전송 |
| `67` | UDP | DHCP server | IP 설정을 제공하는 서버 |
| `68` | UDP | DHCP client | IP 설정을 받는 클라이언트 |
| `123` | UDP | NTP | 시간 동기화 |
| `161` | UDP | SNMP | 네트워크 장비 상태 조회·관리 |
| `162` | UDP | SNMP Trap | 장비가 관리 서버로 이벤트 전송 |

### DNS는 왜 TCP와 UDP를 모두 사용하는가?

일반적인 DNS 질의·응답에는 UDP가 널리 사용된다. 응답 크기, 잘림 처리, 영역 전송, 구현과 프로토콜 요구에 따라 TCP도 사용한다.

시험 답안:

> DNS는 기본 포트 53을 사용하며 UDP와 TCP를 모두 사용할 수 있다.

### DHCP가 포트 두 개를 사용하는 이유

```text
DHCP 서버: UDP 67
DHCP 클라이언트: UDP 68
```

IP 주소를 아직 받지 못한 클라이언트와 서버가 역할별 포트를 이용해 설정 정보를 주고받는다.

## 12. 파일 전송·공유 포트

| 포트 | 전송 | 프로토콜 | 용도 |
|---:|---|---|---|
| `20` | TCP | FTP data | FTP 능동 모드 데이터 |
| `21` | TCP | FTP control | FTP 제어 |
| `22` | TCP | SFTP/SCP over SSH | SSH 기반 보안 파일 전송 |
| `69` | UDP | TFTP | 단순 파일 전송 |
| `445` | TCP | SMB | Windows 파일·프린터 공유 |
| `2049` | TCP/UDP | NFS | Unix/Linux 네트워크 파일 시스템 |

주의:

- FTP와 SFTP는 이름이 비슷하지만 완전히 같은 프로토콜이 아니다.
- SFTP는 SSH 위에서 동작하므로 일반적으로 22번을 사용한다.
- FTPS는 FTP에 TLS를 적용한 방식이고 SFTP와 다르다.

## 13. 데이터베이스·캐시 포트

| 포트 | 전송 | 서비스 | 용도 |
|---:|---|---|---|
| `1433` | TCP | Microsoft SQL Server | SQL Server 기본 연결 |
| `1521` | TCP | Oracle Database | Oracle 리스너에 흔히 사용 |
| `3306` | TCP | MySQL | MySQL 기본 연결 |
| `5432` | TCP | PostgreSQL | PostgreSQL 기본 연결 |
| `6379` | TCP | Redis | Redis 기본 연결 |
| `27017` | TCP | MongoDB | MongoDB 기본 연결 |

중요한 보안 원칙:

> 데이터베이스 포트를 인터넷 전체에 직접 공개하지 말고, 방화벽·사설 네트워크·접근 제어·인증·암호화 등으로 필요한 대상만 접근하게 해야 한다.

Docker 예:

```bash
docker run -d \
  --name postgres \
  -p 5432:5432 \
  postgres
```

이 명령은 호스트 5432를 컨테이너의 PostgreSQL 5432에 연결한다. 학습용 예시이며, 실제 운영에서는 비밀번호·네트워크 노출·볼륨·TLS 등의 보안 설정이 추가로 필요하다.

호스트 포트를 다르게 정할 수도 있다.

```bash
docker run -d \
  --name postgres \
  -p 15432:5432 \
  postgres
```

```text
host:15432 → container:5432
```

컨테이너 안의 PostgreSQL 기본 포트는 5432로 유지하면서 호스트에서는 15432로 접속한다.

## 16. 포트를 확인하는 명령

### macOS·Linux

```bash
lsof -i :8080
```

8080번 포트를 사용하는 프로세스를 확인한다.

```bash
curl -i http://localhost:8080
```

HTTP 서비스의 응답을 확인한다.

환경에 따라 사용할 수 있는 명령:

```bash
ss -lnt
netstat -an
```

옵션을 개념적으로 풀면:

```text
l = listening
n = numeric
t = TCP
```

### Docker

```bash
docker ps
docker port first-nginx-container
docker inspect first-nginx-container
```

`docker ps`의 `PORTS` 열 예:

```text
0.0.0.0:8080->80/tcp
```

해석:

```text
0.0.0.0
└ 모든 IPv4 인터페이스에서 접근을 받을 수 있음

8080->80/tcp
└ 호스트 TCP 8080을 컨테이너 TCP 80에 전달
```

로컬에서만 받도록 주소를 제한하는 예:

```bash
docker run -d \
  -p 127.0.0.1:8080:80 \
  nginx:alpine
```

이 경우 포트는 호스트의 루프백 주소에만 바인딩된다.

## 17. 포트와 보안

### 포트를 바꾸면 안전한가?

SSH를 22에서 2222로 바꾸면 자동 스캔 소음을 일부 줄일 수는 있지만, 근본적인 보안 대책은 아니다.

필요한 보안 대책:

- 필요하지 않은 포트는 열지 않는다.
- 방화벽으로 접근 가능한 출발지를 제한한다.
- 강한 인증을 사용한다.
- 소프트웨어와 운영체제를 업데이트한다.
- TLS 등 암호화를 사용한다.
- 로그를 수집하고 이상 접근을 감시한다.
- 데이터베이스와 관리 API는 가능하면 사설 네트워크에 둔다.

### 열린 포트와 서비스 실행은 같은가?

관련은 있지만 표현을 구분해야 한다.

- 프로그램이 특정 포트에서 **listen**해야 연결을 받을 수 있다.
- 방화벽이 해당 통신을 허용해야 외부 접근이 가능하다.
- Docker에서는 호스트 포트 게시 설정도 필요할 수 있다.
- 클라우드에서는 보안 그룹이나 네트워크 ACL도 영향을 준다.

```text
서비스 실행
    +
주소·포트에서 listen
    +
호스트 방화벽 허용
    +
Docker 포트 게시
    +
외부 네트워크 정책 허용
    =
외부 접속 가능
```

## 18. 시험 예상 질문과 답

### 포트 번호는 무엇인가?

> 한 컴퓨터 안에서 네트워크 통신을 처리할 서비스나 프로세스를 구분하는 0부터 65535 사이의 번호다.

### HTTP와 HTTPS의 기본 포트는?

> HTTP는 80, HTTPS는 443이다.

### SSH와 Telnet의 기본 포트는?

> SSH는 22, Telnet은 23이다. SSH는 통신을 암호화하지만 Telnet은 기본적으로 평문이므로 현대 원격 관리에는 SSH가 사용된다.

### DNS의 기본 포트와 전송 프로토콜은?

> DNS는 53번 포트를 사용하며 UDP와 TCP를 모두 사용할 수 있다.

### `-p 8080:80`의 의미는?

> 호스트의 8080번 포트를 컨테이너의 80번 포트에 연결한다.

### `EXPOSE 80`만으로 호스트에서 접속할 수 있는가?

> 아니다. `EXPOSE`는 사용 예정 포트를 문서화할 뿐이며, 실제 접속 경로를 만들려면 `docker run -p` 같은 포트 게시 설정이 필요하다.

### HTTP는 반드시 80번만 사용해야 하는가?

> 아니다. 80은 등록되고 널리 사용하는 기본 포트지만 서버 설정에 따라 8080 같은 다른 포트에서도 HTTP를 제공할 수 있다.

### TCP 53과 UDP 53은 같은 포트인가?

> 번호는 같지만 전송 프로토콜이 다르므로 서로 구분되는 통신 종단점이다. DNS는 상황에 따라 둘 다 사용한다.

### 0부터 1023까지의 포트 범위 이름은?

> System Ports 또는 Well-Known Ports라고 한다.

### 포트 번호를 변경하면 보안 문제가 해결되는가?

> 아니다. 단순한 포트 변경은 자동 스캔을 일부 줄일 수 있을 뿐이며 방화벽, 접근 통제, 강한 인증, 암호화, 업데이트가 필요하다.

## 최종 한 문장

> IP 주소는 통신할 컴퓨터를 찾고, 포트 번호는 그 컴퓨터 안의 서비스를 구분한다. HTTP 80과 HTTPS 443 같은 번호는 등록된 기본값이지만 강제 고정은 아니며, Docker의 `-p 8080:80`은 호스트 8080번 포트를 컨테이너 80번 포트에 실제로 연결한다.
