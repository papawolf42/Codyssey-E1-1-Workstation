# 0004. 동료평가 기반 예상 문답 · iMac 실습 카드

> 기술 학습 범위의 공식 근거는 `instruction.md`다.
> `image.png`는 **과제 동료평가표**이며 공식 시험지·기출문제·출제 범위표가 아니다.
> 이 문서는 공식 학습 요소와 평가표가 겹치는 부분을 우선 연습하기 위한 예상 자료다.

## 0. 근거와 한계

| 표시 | 의미 |
|---|---|
| `[공식-과제]` | `instruction.md`에 직접 명시된 학습 목표·필수 실습 |
| `[평가표-기반]` | 동료평가표 사진에서 판독한 평가 관점 |
| `[예상]` | 두 자료의 중복을 바탕으로 만든 연습 질문 |
| `[실행확인]` | 이 세션에서 직접 실행해 확인한 결과 |

- 동료평가 문항이 시험에 그대로 나온다는 공식 근거는 없다.
- 특정 포트, 컨테이너 이름, 이미지 태그, 버전, 출력 문구는 정답이 아니다.
- 직접 실행 로그는 Windows 호스트의 Docker Desktop Linux 엔진에서 채집했다. iMac 실기 로그가 아니다.
- Docker 명령은 macOS에서도 대부분 같지만, 호스트 파일 정보 확인은 macOS 문법을 사용해야 한다.
- 로그에는 이름, 이메일, 원격 URL, 토큰, 비밀번호, 개인키를 남기지 않는다.

## 1. 동료평가표에서 읽힌 예상 근거

전체 OCR을 보존하지 않고 시험 대비에 필요한 평가 관점만 정리했다.

- 기능 확인: 터미널 파일 조작, 권한 변경, Docker 상태, `hello-world`, 이미지·컨테이너 관리, Dockerfile 빌드, 포트 접속, 볼륨 영속성, Git·GitHub 연동
- 구조 설명: 디렉터리 구성 기준, 포트·볼륨 절차의 재현성
- 원리 설명: 이미지와 컨테이너, 포트 매핑, 절대·상대 경로, 숫자 권한
- 문제 해결: 포트 충돌, 컨테이너 삭제 후 데이터 손실, `가설 → 확인 → 조치 → 재검증`

사진만으로 작성 기관·작성일·적용 기수와 실제 시험 반영 여부는 확인할 수 없다.

## 2. 공식 학습 요소 체크

`instruction.md` 기준으로 다음을 설명하고 직접 확인할 수 있어야 한다.

- [ ] 절대 경로와 상대 경로의 차이
- [ ] `r/w/x`, `755`, `644` 해석
- [ ] 터미널에서 생성·복사·이동·삭제·내용 확인
- [ ] `docker --version`, `docker info`
- [ ] 이미지·컨테이너 목록, 실행, 중지, 로그, 자원 확인
- [ ] `hello-world`와 Ubuntu 컨테이너 내부 명령
- [ ] `attach`와 `exec` 차이
- [ ] 기존 Dockerfile로 커스텀 이미지 빌드
- [ ] 포트 매핑 후 접속 확인
- [ ] 컨테이너 삭제 후 볼륨 데이터 유지 확인
- [ ] Git과 GitHub의 역할 차이 및 연동 상태
- [ ] 민감정보를 제거한 재현 가능한 증거 기록

Compose, 환경 변수 활용, GitHub SSH는 `instruction.md`에서 선택 보너스다. 필수 대비보다 우선하지 않는다.

## 3. 예상 질문과 답변 키워드

아래 답은 공식 모범답안이 아니라 짧게 말하기 위한 핵심어다.

| 예상 질문 | 답변 키워드 |
|---|---|
| 이미지와 컨테이너의 차이는? | 이미지 = 빌드된 읽기 중심 템플릿, 컨테이너 = 실행 인스턴스와 writable layer, 실행 중 변경은 원본 이미지에 자동 반영되지 않음 |
| 왜 포트 매핑이 필요한가? | 컨테이너 네트워크 격리, 호스트 포트와 서비스가 듣는 컨테이너 포트를 연결, `EXPOSE`만으로 호스트 접속 경로가 생기지는 않음 |
| 포트 충돌은 어떤 순서로 진단하는가? | 오류의 포트 확인 → `docker ps`·`docker port` → macOS `lsof` → 점유 주체 확인 → 내가 만든 대상만 중지하거나 다른 포트 선택 → `curl`·`logs` 재검증 |
| 컨테이너 삭제 뒤 데이터를 남기려면? | writable layer 밖의 named volume 또는 bind mount 사용, 컨테이너와 데이터 수명 분리, 중요 데이터는 별도 백업 |
| 절대·상대 경로는 언제 쓰는가? | 절대 경로는 현재 위치와 무관한 고정 대상, 상대 경로는 현재 위치 기준이며 프로젝트 이동성과 재사용에 유리 |
| `755`, `644`는 어떻게 계산하는가? | `r=4`, `w=2`, `x=1`; 사용자·그룹·기타 순서; `755=rwxr-xr-x`, `644=rw-r--r--` |
| Dockerfile 빌드 과정을 설명하라. | Dockerfile·빌드 컨텍스트 확인 → `docker build -t` → `docker images` 또는 `inspect` → 컨테이너 실행 → 기능 검증 |
| `attach`와 `exec`의 차이는? | `attach`는 기존 메인 프로세스 입출력에 연결, `exec`는 실행 중 컨테이너에 새 프로세스 실행; 점검에는 보통 `exec`가 안전 |
| Git과 GitHub의 차이는? | Git = 로컬 버전 관리, GitHub = 원격 저장·협업 서비스, `commit`은 로컬 이력, `push`는 원격 전송 |
| 구조를 어떻게 재현 가능하게 만들었는가? | 빌드 정의·입력 파일·실행 문서 분리, 변수와 실행 순서 명시, 명령과 기대 결과 및 정리 방법 기록 |
| 어려운 문제를 어떻게 설명할 것인가? | 증상 → 가설 → 확인 명령과 관찰 → 최소 조치 → 같은 기준으로 재검증 → 재발 방지 |

### 15초 답변 뼈대

```text
원리 한 문장
→ 확인에 쓴 명령
→ 출력에서 본 근거
→ 실패했다면 조치와 재검증
```

## 4. iMac/macOS 짧은 실습 카드

### 4.1 터미널·경로·권한

```bash
START_DIR="$PWD"
PRACTICE_TMP_ROOT="${TMPDIR:-/tmp}"
LAB_DIR="$(mktemp -d "${PRACTICE_TMP_ROOT%/}/exam-practice.XXXXXX")"
cd "$LAB_DIR"

pwd
ls -la
mkdir source
printf '%s\n' practice > source/note.txt
cat source/note.txt
cp source/note.txt copy.txt
mv copy.txt moved.txt

chmod 600 moved.txt
chmod 700 source
stat -f 'before %Sp %OLp %N' moved.txt source

chmod 644 moved.txt
chmod 755 source
stat -f 'after  %Sp %OLp %N' moved.txt source
printf 'relative=%s\nabsolute=%s\n' './moved.txt' "$PWD/moved.txt"

rm moved.txt source/note.txt
rmdir source
cd "$START_DIR"
rmdir "$LAB_DIR"
```

macOS는 숫자 권한 확인에 `stat -f`를 쓴다. GNU/Linux의 `stat -c`와 혼동하지 않는다.

### 4.2 Docker 상태·기본 운영

```bash
docker --version
docker info
docker run --rm hello-world
docker images
docker ps
docker ps -a
```

- `docker --version`만 성공하면 CLI 존재만 확인한 것이다.
- daemon 통신 여부는 `docker info` 또는 실제 컨테이너 실행으로 확인한다.
- 이미지 다운로드 실패는 daemon 장애인지 네트워크·레지스트리 문제인지 오류 원문으로 구분한다.

### 4.3 Ubuntu·`attach`·`exec`

```bash
RUN_ID="$(date +%s)-$$"
SHELL_CONTAINER="practice-shell-${RUN_ID}"

docker pull ubuntu
docker run -dit --name "$SHELL_CONTAINER" ubuntu bash
docker exec "$SHELL_CONTAINER" bash -lc 'pwd; ls /; echo exec-ok'
docker ps --filter "name=${SHELL_CONTAINER}"
docker stats --no-stream "$SHELL_CONTAINER"
```

`attach`를 직접 비교할 때:

```bash
docker attach "$SHELL_CONTAINER"
```

- 붙은 뒤 컨테이너를 계속 실행한 채 빠져나오려면 `Ctrl-p`, `Ctrl-q`를 차례로 누른다.
- `exit` 또는 `Ctrl-C`는 메인 프로세스에 영향을 줄 수 있다.
- 다시 점검할 때는 `docker exec "$SHELL_CONTAINER" ...`를 사용한다.

### 4.4 Dockerfile 빌드·동적 포트 접속

먼저 `SERVICE_PORT`를 **Dockerfile 또는 애플리케이션이 실제로 수신하는 포트 숫자**로 바꾼다. 정해진 시험 포트는 없다.

```bash
RUN_ID="$(date +%s)-$$"
SERVICE_PORT='<실제 서비스 포트>'
IMAGE_TAG="practice-image:${RUN_ID}"
WEB_CONTAINER="practice-web-${RUN_ID}"

test -f Dockerfile
docker build -t "$IMAGE_TAG" .
docker images "$IMAGE_TAG"

docker run -d --name "$WEB_CONTAINER" \
  -p "127.0.0.1::${SERVICE_PORT}" "$IMAGE_TAG"

docker port "$WEB_CONTAINER" "${SERVICE_PORT}/tcp"
HOST_PORT="$(docker port "$WEB_CONTAINER" "${SERVICE_PORT}/tcp" | head -n 1 | awk -F: '{print $NF}')"
curl -fsS --max-time 5 "http://127.0.0.1:${HOST_PORT}/"
docker logs --tail 20 "$WEB_CONTAINER"
docker stats --no-stream "$WEB_CONTAINER"
```

`-p 127.0.0.1::컨테이너포트`는 빈 호스트 포트를 Docker가 고르게 한다. 출력된 실제 매핑을 `docker port`로 확인한다.

### 4.5 포트 충돌 진단

```bash
docker ps --format 'table {{.Names}}\t{{.Ports}}'
docker port "$WEB_CONTAINER"
lsof -nP -iTCP:"$HOST_PORT" -sTCP:LISTEN
docker inspect "$WEB_CONTAINER"
docker logs --tail 20 "$WEB_CONTAINER"
```

점유 PID나 컨테이너를 바로 강제 종료하지 않는다. 내가 만든 대상인지 확인한 뒤 중지하거나 다른 빈 호스트 포트를 선택한다.

### 4.6 볼륨 영속성

```bash
RUN_ID="$(date +%s)-$$"
VOLUME_NAME="practice-volume-${RUN_ID}"
WRITER_CONTAINER="practice-writer-${RUN_ID}"

docker volume create "$VOLUME_NAME"
docker run --name "$WRITER_CONTAINER" \
  --mount "type=volume,src=${VOLUME_NAME},dst=/data" \
  ubuntu bash -lc 'printf "%s\n" persisted > /data/proof.txt'

docker rm "$WRITER_CONTAINER"
docker run --rm \
  --mount "type=volume,src=${VOLUME_NAME},dst=/data,readonly" \
  ubuntu cat /data/proof.txt
```

두 번째 컨테이너에서 `persisted`가 출력되어야 컨테이너 삭제 후에도 데이터가 유지됐다는 증거다.

### 4.7 Git·GitHub 상태 확인

```bash
git --version
if git config --get user.name >/dev/null; then echo 'user.name=SET'; else echo 'user.name=NOT_SET'; fi
if git config --get user.email >/dev/null; then echo 'user.email=SET'; else echo 'user.email=NOT_SET'; fi
git status
git remote
```

네트워크 사용이 허용되고 `origin`이 있을 때만 원격 조회를 추가한다.

```bash
GIT_TERMINAL_PROMPT=0 git ls-remote --exit-code origin HEAD
```

- 원격 조회 성공은 push 권한까지 증명하지 않는다.
- `git config --list`, `git remote -v` 같은 원문을 제출하기 전 개인정보·자격증명 포함 여부를 확인한다.

### 4.8 내가 만든 리소스만 정리

먼저 변수의 값과 조회 결과가 내가 만든 대상을 가리키는지 확인한다.

```bash
printf '%s\n' "$SHELL_CONTAINER" "$WEB_CONTAINER" "$VOLUME_NAME" "$IMAGE_TAG"
docker ps -a --filter "name=${SHELL_CONTAINER}"
docker ps -a --filter "name=${WEB_CONTAINER}"
docker volume inspect "$VOLUME_NAME"
docker image inspect "$IMAGE_TAG"
```

확인 후 정확한 이름만 정리한다.

```bash
docker stop "$SHELL_CONTAINER" "$WEB_CONTAINER"
docker rm "$SHELL_CONTAINER" "$WEB_CONTAINER"
docker volume rm "$VOLUME_NAME"
docker image rm "$IMAGE_TAG"
```

공유 iMac에서는 `docker system prune`, `docker container prune`, `docker image prune`, `docker volume prune`를 사용하지 않는다.

## 5. 직접 실행해 확인한 핵심 증거

<details>
<summary>Windows Docker Desktop에서 얻은 최소 증거 펼치기</summary>

이 로그는 명령 원리를 검증하기 위한 참고 자료다. 환경 고유 버전·해시·포트·리소스 이름은 제거했다.

### 권한과 경로

```text
before directory=700 file=600
relative=./moved.txt
absolute=/tmp/exam-lab/moved.txt
after  directory=755 file=644
cleanup=OK
```

판정: 파일 조작과 권한 전후 비교에 성공했다.

### Docker daemon과 `hello-world`

```text
docker info: server 응답 확인
Hello from Docker!
```

판정: CLI가 daemon과 통신했고 컨테이너 생성·실행·출력 전달에 성공했다.

### 빌드·포트·접속

```text
load build definition from Dockerfile
exporting to image
container=running
binding=127.0.0.1:<동적 호스트 포트>-><컨테이너 포트>/tcp
HTTP response=OK
```

판정: Dockerfile 빌드, 컨테이너 실행, 동적 포트 매핑, HTTP 접속에 성공했다.

### 이미지와 컨테이너 변경 분리

```text
container-layer-only
fresh_container_has_change=false
```

판정: 한 컨테이너의 writable layer 변경이 같은 이미지의 새 컨테이너에 나타나지 않았다.

### 포트 충돌

```text
Bind for 0.0.0.0:<호스트 포트> failed: port is already allocated
failed_container_status=Created
```

판정: 이미 점유된 호스트 포트 요청이 실패하며, 오류·컨테이너 상태·리스닝 소켓으로 원인을 좁힐 수 있었다.

### 볼륨 영속성

```text
writer_container=removed
restored=persisted-after-container-removal
```

판정: 첫 컨테이너 삭제 뒤 두 번째 컨테이너가 같은 named volume의 파일을 읽었다.

### `logs`·`exec`·`stats`·`attach`

```text
logs=main-process-output-confirmed
exec=OK
stats=one-shot-collected
attach=main-process-stream-confirmed
```

판정: 각 명령의 관찰 대상을 구분해 확인했다.

### Git·GitHub

```text
inside_work_tree=true
remote_head_reachable=true
```

판정: Git 저장소와 원격 `HEAD` 조회를 확인했다. 사용자 정보와 원격 URL은 출력하지 않았다.

### 실제 문제 해결 예

```text
증상: 컨테이너가 Exited (127)
오류: 실행 명령을 찾지 못함
확인: docker ps -a → docker logs → docker inspect → 이미지 내부 명령 존재 여부
조치: Dockerfile의 실행 명령을 실제 존재하는 명령으로 수정
재검증: build 성공 → container running → docker port 확인 → HTTP 응답 확인
```

핵심은 특정 웹 서버나 이미지가 아니라 `오류 원문 → 가설 → 확인 → 최소 변경 → 재검증` 순서다.

## 6. 시험 직전 암기 카드

```text
이미지 = 빌드된 템플릿
컨테이너 = 이미지의 실행 인스턴스
포트 매핑 = 호스트 접근 경로
볼륨 = 컨테이너와 데이터 수명 분리
Git = 로컬 이력 관리
GitHub = 원격 저장·협업
오류 대응 = 원문 → 가설 → 확인 → 조치 → 재검증
```

실습 답변은 항상 다음 순서로 끝낸다.

```text
실행한 명령
→ 출력에서 확인한 사실
→ 그 사실이 증명하는 원리
→ 실패했다면 조치와 재검증 결과
```
