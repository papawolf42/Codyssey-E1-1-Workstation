## 2. 경로와 터미널

### 절대 경로와 상대 경로

- **절대 경로:** 파일 시스템의 루트 `/`부터 전체 위치를 표현한다. 현재 작업 디렉터리와 무관하다.
- **상대 경로:** 현재 작업 디렉터리를 기준으로 해석한다.

```console
pwd
cat /absolute/path/to/file
cat ./relative/path/to/file
cat ../file
```

- `.`: 현재 디렉터리
- `..`: 상위 디렉터리
- 상대 경로를 사용할 때는 `pwd`로 기준 위치를 먼저 확인한다.
- 프로젝트 내부 파일은 상대 경로가 이동성에 유리하다.
- 특정 위치를 정확히 지정해야 할 때는 절대 경로가 명확하다.

**예상 답안**

> 절대 경로는 루트부터 전체 위치를 표현하므로 현재 위치와 무관하다. 상대 경로는 현재 작업 디렉터리를 기준으로 해석된다. 따라서 상대 경로를 사용할 때는 `pwd`로 기준 위치를 확인해야 한다.

### 필수 터미널 조작

```console
pwd
ls
ls -la
cd <DIRECTORY>
mkdir <DIRECTORY>
touch <FILE>
cat <FILE>
cp <SOURCE> <DESTINATION>
mv <SOURCE> <DESTINATION>
rm <FILE>
rmdir <EMPTY_DIRECTORY>
```

| 명령 | 핵심 용도 |
|---|---|
| `pwd` | 현재 위치 확인 |
| `ls -la` | 숨김 항목을 포함한 상세 목록 |
| `cd` | 디렉터리 이동 |
| `mkdir` | 디렉터리 생성 |
| `touch` | 빈 파일 생성 또는 수정 시각 갱신 |
| `cat` | 파일 내용 출력 |
| `cp` | 복사 |
| `mv` | 이동 또는 이름 변경 |
| `rm` | 파일 삭제 |
| `rmdir` | 빈 디렉터리 삭제 |

## 3. 파일과 디렉터리 권한

### 숫자 계산

| 권한 | 의미 | 값 |
|---|---|---:|
| `r` | 읽기 | 4 |
| `w` | 쓰기 | 2 |
| `x` | 실행 또는 탐색 | 1 |

세 자리는 소유자(user), 그룹(group), 기타 사용자(others) 순서다.

```text
7 = 4 + 2 + 1 = rwx
6 = 4 + 2     = rw-
5 = 4 + 1     = r-x

755 = rwxr-xr-x
644 = rw-r--r--
```

### 파일과 디렉터리에서의 의미

| 권한 | 파일 | 디렉터리 |
|---|---|---|
| `r` | 내용 읽기 | 이름 목록 읽기 |
| `w` | 내용 수정 | 항목 생성·삭제·이름 변경 |
| `x` | 파일 실행 | 진입하고 내부 경로 탐색 |

디렉터리의 `x`는 프로그램 실행 권한이 아니라 **경로 통과·탐색 권한**이다.

```console
ls -l <FILE>
ls -ld <DIRECTORY>
chmod 644 <FILE>
chmod 755 <DIRECTORY>
```

**예상 답안**

> 숫자 권한은 `r=4`, `w=2`, `x=1`을 소유자·그룹·기타 사용자별로 합산한다. `755`는 `rwxr-xr-x`, `644`는 `rw-r--r--`이다. 디렉터리의 `x`는 진입과 내부 경로 탐색을 허용한다.

## 4. Docker 핵심 구조

### 이미지, 컨테이너, Dockerfile

| 개념 | 정의 |
|---|---|
| 이미지 | 컨테이너를 만들기 위한 읽기 전용 템플릿 |
| 컨테이너 | 이미지로 만든 실행 인스턴스 |
| Dockerfile | 이미지를 재현 가능하게 빌드하기 위한 명령 정의서 |

```text
Dockerfile + 소스
        │ docker build
        ▼
      이미지
        │ docker run
        ▼
     컨테이너
```

- `docker build`의 결과는 이미지다.
- `docker run`은 이미지에서 컨테이너를 생성하고 실행한다.
- 컨테이너 삭제와 이미지 삭제는 서로 다른 작업이다.
- Dockerfile의 `COPY`는 빌드 컨텍스트 안의 파일을 이미지에 포함한다.

### 대표 Dockerfile 명령

| 명령 | 역할 |
|---|---|
| `FROM` | 베이스 이미지 선택 |
| `COPY` | 빌드 컨텍스트의 파일을 이미지에 복사 |
| `RUN` | 이미지 빌드 중 명령 실행 |
| `ENV` | 환경 변수 설정 |
| `EXPOSE` | 컨테이너가 사용할 포트를 설명 |
| `CMD` | 기본 실행 명령 지정 |
| `HEALTHCHECK` | 컨테이너 상태 점검 방법 정의 |

모든 명령이 반드시 들어가야 한다는 뜻은 아니다. 공식 요구는 기존 Dockerfile을 바탕으로 정적 콘텐츠를 바꾸거나 패키지·사용자·환경 변수·헬스체크 등을 추가해 커스텀 이미지를 만드는 것이다(`instruction.md:107-110`).

### 기본 점검과 운영

```console
docker --version
docker info
docker pull <IMAGE>
docker images
docker ps
docker ps -a
docker logs <CONTAINER>
docker stats --no-stream <CONTAINER>
docker stop <CONTAINER>
```

| 명령 | 확인 대상 |
|---|---|
| `docker --version` | Docker CLI 설치와 버전 |
| `docker info` | Client와 daemon(Server)의 통신 및 환경 |
| `docker images` | 로컬 이미지 |
| `docker ps` | 실행 중인 컨테이너 |
| `docker ps -a` | 종료된 항목을 포함한 전체 컨테이너 |
| `docker logs` | 컨테이너 프로세스의 표준 출력·오류 |
| `docker stats` | CPU·메모리 등 리소스 사용 |

### `attach`와 `exec`

- `docker attach`: 실행 중인 컨테이너의 기존 메인 프로세스 입출력에 연결한다.
- `docker exec`: 실행 중인 컨테이너에서 새 프로세스를 실행한다.

```console
docker attach <CONTAINER>
docker exec -it <CONTAINER> <SHELL>
```

**예상 답안**

> `attach`는 기존 메인 프로세스에 연결하고, `exec`는 실행 중인 컨테이너 안에서 별도의 새 프로세스를 실행한다.

## 5. Dockerfile 빌드와 포트 매핑

### 일반적인 빌드·실행 형태

```console
docker build -t <IMAGE>:<TAG> <BUILD_CONTEXT>
docker run -d --name <CONTAINER> -p <HOST_PORT>:<CONTAINER_PORT> <IMAGE>:<TAG>
```

`docker build ... .`의 마지막 `.`은 현재 디렉터리를 빌드 컨텍스트로 사용한다는 뜻이다. `COPY` 원본은 빌드 컨텍스트 안에 있어야 한다.

### 포트 매핑이 필요한 이유

컨테이너는 호스트와 분리된 네트워크 환경에서 실행된다. 컨테이너 내부 서비스 포트는 호스트에 자동으로 연결되지 않으므로 포트를 게시해야 한다.

```text
-p <HOST_PORT>:<CONTAINER_PORT>
```

- 왼쪽: 호스트에서 접속할 포트
- 오른쪽: 컨테이너 내부 서비스가 사용하는 포트

Dockerfile의 `EXPOSE`는 포트 사용 의도를 설명하지만 실제 호스트 포트 전달 규칙을 만들지는 않는다. 실제 전달은 `docker run -p`로 설정한다.

```console
curl http://localhost:<HOST_PORT>
docker ps
docker logs <CONTAINER>
```

**예상 답안**

> 컨테이너는 호스트와 분리된 네트워크에서 실행되므로 내부 서비스 포트가 자동으로 공개되지 않는다. `-p <호스트 포트>:<컨테이너 포트>`로 호스트 요청을 컨테이너 서비스에 전달한다.

## 6. 바인드 마운트와 Docker 볼륨

| 항목 | 바인드 마운트 | Docker 볼륨 |
|---|---|---|
| 원본 위치 | 사용자가 지정한 호스트 경로 | Docker가 관리하는 저장소 |
| 주 용도 | 호스트 파일 변경을 즉시 반영 | 컨테이너와 분리된 영속 데이터 |
| 호스트 경로 의존 | 높음 | 낮음 |
| 컨테이너 삭제 후 데이터 | 호스트에 남음 | 볼륨을 삭제하지 않으면 남음 |

### 바인드 마운트

```console
docker run --mount type=bind,src=<HOST_PATH>,dst=<CONTAINER_PATH> <IMAGE>
```

공식 검증 핵심은 **호스트 파일 변경 전후를 비교해 컨테이너에 반영되는지 확인**하는 것이다(`instruction.md:57-59`).

### Docker 볼륨

```console
docker volume create <VOLUME>

docker run --name <CONTAINER_A> --mount type=volume,src=<VOLUME>,dst=<CONTAINER_PATH> <IMAGE>
```

영속성 검증 순서:

1. 볼륨 생성
2. 첫 컨테이너에 연결
3. 마운트 경로에 데이터 저장
4. 첫 컨테이너 삭제
5. 새 컨테이너에 같은 볼륨 연결
6. 기존 데이터가 남았는지 확인

**예상 답안**

> 바인드 마운트는 사용자가 지정한 호스트 경로를 직접 연결한다. Docker 볼륨은 Docker가 관리하며 컨테이너를 삭제해도 볼륨을 삭제하지 않으면 데이터가 유지된다.

## 7. Git과 GitHub

### 역할 차이

| 항목 | Git | GitHub |
|---|---|---|
| 정체 | 분산 버전 관리 도구 | Git 원격 저장소·협업 서비스 |
| 기본 위치 | 로컬 컴퓨터 | 원격 서버 |
| 핵심 역할 | 변경 추적, 커밋, 브랜치 | 공유, 백업, 협업 |

```text
작업 파일
  │ git add
  ▼
스테이징 영역
  │ git commit
  ▼
로컬 저장소
  │ git push
  ▼
GitHub 원격 저장소
```

### 설정과 확인

```console
git config --list
git config user.name
git config user.email
git status
git add <FILE>
git commit -m "<MESSAGE>"
git remote -v
git push origin <BRANCH>
```

- `add`: 다음 커밋에 포함할 변경을 스테이징한다.
- `commit`: 로컬 저장소에 변경 이력을 만든다.
- `push`: 로컬 커밋을 원격 저장소로 보낸다.

**예상 답안**

> Git은 로컬에서 변경 이력을 관리하는 버전 관리 도구이고, GitHub는 Git 저장소를 원격에 보관하고 공유·협업하게 하는 서비스다. `commit`은 로컬 이력을 만들고 `push`는 그 이력을 원격으로 전송한다.

## 8. 보안과 검증 기록

공식 문서는 토큰·비밀번호·개인키를 로그와 이미지에 남기지 말고 마스킹하도록 요구한다(`instruction.md:122-124`, `155-158`).

- 민감정보를 문서·스크린샷·커밋에 넣지 않는다.
- 노출된 자격증명은 제거만 하지 말고 폐기한 뒤 재발급한다.
- 명령어와 출력 결과를 함께 기록한다.
- 트러블슈팅은 `문제 → 원인 → 해결 → 검증`으로 정리한다.

```text
문제: 어떤 명령에서 어떤 증상이 발생했는가?
원인: 어떤 상태나 설정 때문에 발생했는가?
해결: 무엇을 변경했는가?
검증: 어떤 명령과 결과로 해결을 확인했는가?
```
